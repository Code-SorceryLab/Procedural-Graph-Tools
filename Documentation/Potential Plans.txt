GRAPH GRAMMAR UPGRADES:

4. Spatial Resolution Hooks The Limitation: When is_new spawns a node, it places it at the exact mathematical midpoint (pos_a + pos_b) / 2.0. In a dense graph, rewriting a few edges will cause multiple nodes to visually pile up on the same coordinate.The Upgrade: We can hook the grammar engine directly into your physics system. When the grammar injects a new node, it triggers a localized spatial relaxation (a quick burst of repulsive forces just for the new node and its immediate neighbors) so the graph automatically untangles itself during the rewrite process.















Problem

GenerateGrid creates nodes with fixed IDs like grid:0:0, grid:1:0, etc. When run as a generator in a full pipeline, the pipeline controller clears the graph first, so these IDs are safe.

However, when run using Live Apply (additive mode) from the PipelineController, the graph is not cleared. If the graph already contains nodes from a previous run of GenerateGrid (or any other modifier that created grid: prefixed IDs), the new nodes will collide with existing IDs. In Godot, Graph.add_node checks if the ID already exists and silently does nothing, which means:

    Nodes are not duplicated—they simply fail to appear.

    Edges may be created to the old nodes instead of new ones, leading to incorrect topology.

    The user sees no error, just a missing or corrupted result.

This problem is not limited to GenerateGrid; any generator that uses deterministic, fixed IDs (e.g., GeneratePolar, GenerateDAG) will have the same issue if it can be executed in Live Apply mode.
Why It Happens

    GenerateGrid.execute assumes a clean slate.

    The PipelineController’s Live Apply button does not perform the destructive wipe that the full pipeline run does for generators.

    There is currently no mechanism for a generator to know whether the graph is empty or to generate unique IDs based on the current graph state.

Potential Fixes
1. Disable Live Apply for Generators

Simplest and most robust: in PipelineController, if the selected modifier’s category is GENERATOR, hide or disable the “Apply (Additive)” button. Only allow “Generate (Wipe & Apply)” for generators. This matches the semantic expectation that generators always start fresh.

Pros: No ID generation changes needed. Prevents the problem entirely.
Cons: Removes the flexibility of adding multiple grids to the same graph additively. But that’s a rare use case.
2. Generate Unique IDs Using a Batch Token

Add a unique token to the pipeline_context for every Live Apply action. GenerateGrid (and other generators) can then incorporate this token into the node IDs, e.g., grid_live123:0:0.

Pros: Allows additive generator use; no errors; deterministic if the token is seeded.
Cons: IDs become longer and less human‑readable; need to ensure the token is passed correctly through the pipeline context; still leaves the possibility of duplicate edges if the same token is used twice (which is why tokens must be unique per action).
3. Incrementing Internal Counter for IDs

GenerateGrid could call recorder.get_next_display_id() (or a dedicated node counter) to generate a unique prefix each time it runs. For example, grid_1:0:0, grid_2:0:0, etc., where the number increments every time the graph is modified.

Pros: Automatic uniqueness, no token management.
Cons: Node IDs become non‑deterministic unless the counter itself is reset during a pipeline (which would break reproducibility); may cause issues with save/load if the counter is not saved.
4. Detect Collisions and Re‑seed Automatically

Before adding a node, GenerateGrid could check if grid:0:0 already exists. If it does, increment a suffix and re‑generate the whole grid with that suffix until it finds a free namespace.

Pros: No external changes needed; works transparently.
Cons: Potential performance hit for large grids; not fully deterministic if the existing graph state varies (but for Live Apply, that’s acceptable).
Recommended Long‑Term Approach

Combine #1 and #2:

    Keep the full pipeline semantics unchanged (generators wipe first).

    In PipelineController, disable Live Apply for generators to avoid the most common accidental misuse.

    For advanced users who want additive generation, implement the batch token system so that any generator can safely run additively if the controller passes a unique token in pipeline_context. This gives both safety and flexibility.

Until then, the simplest immediate fix is to disable Live Apply for generators. You can revisit the token approach when you’re ready to support additive generation of fixed‑ID graphs.

2. Strategy Pipeline / Multi‑Pass Generation

Leverages: StrategyExecutor, GraphRecorder, CmdBatch

    What it does – allow chaining of strategies. For example, run StrategyGrid to create a base layout, then pipe the result into StrategyWalker to add agents that carve new paths, then run BuoyancyEngine for organic layout. Each pass is a separate undoable batch.

    Why it matters – most real‑world PCG pipelines are composites. Enabling this natively means developers can prototype entire dungeon‑generation pipelines inside the editor, and researchers can study how successive algorithms interact.

3. Visual Metrics Dashboard (Heatmaps & Overlays)

Leverages: GraphMetrics, GraphRenderer, SemanticRegistry

    What it does – instead of only showing metrics as text, colour‑code the graph. For example, overlay betweenness centrality as a heatmap (red nodes = highly central), or highlight all bridges in orange, or show a flow‑bottleneck overlay. The user can toggle these visualisations on/off.

    Why it matters – visual feedback is the quickest way for a designer to understand the structure of a generated graph. It bridges the gap between numeric analysis and human intuition, making it useful both for debugging PCG algorithms and for teaching graph theory.

4. Step‑by‑Step Simulation Playback

Leverages: Simulation, AgentWalker, GraphRecorder

    What it does – record the entire simulation history (agent positions, edge changes, painting actions) and allow the user to scrub backward/forward through each tick, highlight agent paths, and inspect state at any point.

    Why it matters – debugging agent behaviour is currently done with print() statements. A visual timeline lets developers understand why an agent got stuck or when a maze dead‑end was created. For researchers, it enables qualitative analysis of algorithm behaviour.

5. Python / External Scripting Node

Leverages: GraphRecorder, CmdSetProperty, custom strategy system

    What it does – a special “Python Node” (or Lua) that can be placed inside a strategy pipeline. The user writes a small script that receives the current graph state and can return a batch of commands (add nodes, change properties, etc.).

    Why it matters – this opens the tool to the entire Python ecosystem (NumPy, SciPy, PyTorch) without requiring a full plugin API. Researchers can prototype a new algorithm in Python and immediately see the results inside the editor.

6. Collaborative & Reproducible Graph Packages

Leverages: GraphSerializer, SemanticRegistry

    What it does – package a graph together with its strategy settings, custom semantic definitions, and a metadata block (author, description, DOI) into a single .pcgpack file. Optionally generate a static HTML preview that renders the graph with metrics.

    Why it matters – makes it easy to share complete, reproducible PCG experiments. A researcher can publish a graph package alongside a paper, and another researcher can load it, re‑run the generation with the exact same seed, and verify the results.

7. Export to Tilemap / 3D Mesh

Leverages: Graph, GraphZone, GraphSettings

    What it does – interpret the graph (optionally with zone data) as a dungeon layout and export it to Godot’s TileMap or GridMap, or as a 3D mesh for external engines. Node types map to tiles (e.g., “corridor” → floor tile, “spawn” → player start).

    Why it matters – this is the direct bridge from the research/prototyping environment to a playable game. Developers can generate a level, tweak it visually, and export a ready‑to‑use game asset.

8. In‑Editor Graph Query Language

Leverages: Graph, SemanticRegistry, InspectorController

    What it does – a simple query bar where the user can type SELECT nodes WHERE type='boss' AND depth > 5 or SELECT edges WHERE weight > 2.0 to highlight and possibly batch‑edit matching elements.

    Why it matters – as graphs grow large, manually finding nodes with specific properties becomes tedious. This is a lightweight alternative to full scripting and is useful for both debugging and content authoring.

1. Monte Carlo Playtesting & Heatmap Analytics

What it is – Run many agents in fast “headless” mode, aggregate their paths, and render edge/heatmap overlays.

Relationship to our existing ideas

    Directly extends #4 (Simulation Playback) and #3 (Visual Metrics Overlays).

    Overlaps with #1 (Parameter‑Sweep Runner) if you sweep agent behaviour parameters.

    The heatmap visualisation is exactly the kind of overlay we planned for betweenness, bridges, etc.

Feasibility / Architecture

    Your Simulation already runs agents as fast as the CPU allows. A headless mode would skip redraws and batch GraphRecorder commands for speed, then discard them (since we only want aggregated stats, not undoable mutations).

    The heavy lifting is data collection per tick (agent position, step count, is_finished, bump events). The Simulation already snapshots these; we’d need to store them in an array for the run and then merge into edge‑usage counts, death‑node counts, etc.

    The GraphRenderer already supports arbitrary drawing layers (the _draw_layer_* pattern). Adding a _draw_layer_heatmap() that reads a Dictionary of edge‑usage frequencies and colours edges accordingly is straightforward.

Value

    For researchers: quantitative evaluation of navigability, dead‑ends, and flow.

    For developers: see at a glance which corridors are under‑ or over‑used, informing level design tweaks.

Suggested implementation path

    Add a “Monte Carlo” panel to the AnalysisController (or a new controller) with run count, agent behaviour settings, and a “Run & Visualize” button.

    Create a MonteCarloRunner that calls Simulation.step() in a tight loop, accumulating stats into a MonteCarloReport resource.

    Expose the report as a new overlay in GraphRenderer, using draw_line with alpha/width proportional to usage.

2. Hierarchical Sub‑Graphs (Nested Topologies)

What it is – A node can contain a whole sub‑graph; double‑clicking “enters” that sub‑graph, with a breadcrumb trail to go back up.

Relationship to our existing ideas

    This is entirely new and not covered by any previous suggestion. It’s a fundamental data model extension.

    It naturally synergizes with #2 (Strategy Pipeline) because you could apply a strategy that generates a continent graph, then a nested strategy that fills each city node with a street graph.

Feasibility / Architecture

    Data model: NodeData would gain an optional sub_graph: Graph property. The Graph itself doesn’t need to change because the sub‑graph is just another Graph resource.

    Editor UX: GraphEditor currently owns a single graph. We would need to introduce a graph_stack: Array[Graph] to push/pop as the user enters/exits containers. The GraphRenderer, GraphCamera, and InspectorController would need to accept a current_graph that can be swapped.

    Breadcrumb UI: A simple bar showing World > Dungeon_A > BossRoom, clickable to navigate back.

    Serialization: GraphSerializer would need to recursively serialize sub‑graphs. This is a moderate change, but the recursive structure is straightforward.

    Performance: Each sub‑graph is isolated; the editor only draws one at a time, so no performance hit.

Value

    Game‑changing for world‑scale generation: you can have a strategy that generates a world map of nodes, then click into any node to generate its interior using a different strategy.

    Enables multiscale graph research: analysing how local structure affects global properties.

Suggested implementation path

    Add sub_graph to NodeData.

    Refactor GraphEditor to support _current_graph and a stack of parent graphs.

    Update GraphRenderer and all tools to reference editor.current_graph instead of editor.graph.

    Add double‑click detection on container nodes to push/pop the graph stack.

    Update GraphSerializer to recursively save/load sub‑graphs.

    Add breadcrumb UI.

This is a large, high‑impact feature. It’s best done after the core undo/edge refactoring is completely stable and the simpler overlays are in place.
3. Topological Rasterization (Graph‑to‑TileMap)

What it is – Convert the abstract graph + zones into a physical Godot TileMapLayer or GridMap using WFC or marching squares.

Relationship to our existing ideas

    This is a more advanced version of #7 (Export to Tilemap/Mesh). Our original idea was a simpler direct mapping (type → tile). This adds sophisticated geometry generation.

Feasibility / Architecture

    The Graph already has spatial information (node.position, GraphSettings.GRID_SPACING, GraphZone cells).

    A new GraphRealizer utility could read the graph and produce a TileMap data dictionary.

    WFC integration is more complex but can be modular: a StrategyWFC could be written that takes a graph as input and outputs tile constraints.

    The output would be a Godot TileMapLayer node, which could be added to the scene or saved as a .tscn file.

    This doesn’t change the core architecture; it’s a new consumer of the existing data.

Value

    Directly bridges the gap from research to game. A developer can generate a graph, see it in 3D, and playtest immediately.

    Researchers can evaluate how topological properties translate into spatial layouts, which is a hot topic in PCG.

Suggested implementation path

    Start with a simple “Graph → TileMap” exporter that uses node type to pick a tile, draws edges as corridors, and respects zone types for terrain.

    Later, add a WFC strategy that uses the graph as constraints to produce more organic, tile‑based layouts.

    The result can be previewed in a separate viewport or saved as a scene.
