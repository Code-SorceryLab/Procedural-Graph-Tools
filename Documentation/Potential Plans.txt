# Procedural Graph Editor - Architecture & Roadmap

## Current Engine State
- **Semantic Registry:** A unified data structure handling customized semantic types and properties across four distinct targets: `NODE`, `EDGE`, `AGENT`, and `ZONE`.
- **Universal Undo/Redo:** The `GraphHistory` and `CmdBatch` systems faithfully record data mutations across all targets, utilizing deep copies (`.duplicate(true)`) to prevent reference mutations.
- **Contextual Hit Detection & UI:** Tools share base hit-detection logic. The editor provides live, contextual hover-glow feedback depending on which semantic object the active tool targets. Omni-box selection allows grabbing multiple targets concurrently.
- **Agent Capabilities:** `AgentWalker` operates via a Capability/Brain architecture. The `CapPainter` allows agents to procedurally alter node types, edge weights, and custom properties as they traverse the graph.

## Future Development Paths

### 1. Force-Directed Layout (Buoyancy / Physics)
**Goal:** Automatically untangle messy procedurally generated graphs.
**Implementation:** Implement a Fruchterman-Reingold style physics step. Nodes act as repelling magnets (Coulomb's law); Edges act as attracting springs (Hooke's law). 
**UI:** Driven by a continuous "Buoyancy Mode" toggle in the top menu bar, allowing the user to watch the graph organically untangle in real-time.

### 2. Directed Acyclic Graphs (DAG) & Questlines
**Goal:** Introduce logical constraint solving to represent progression systems, tech trees, or narrative questlines.
**Implementation:** Create a `StrategyQuestGen` that enforces acyclic flows. Agents or generators will flag nodes with semantic data (e.g., `required_item`, `boss_encounter`) and dynamically update edge `lock_level` properties to ensure a mathematically solvable progression puzzle.

Mode A: The Architect (Generative)
You give it a blank canvas, a number of nodes, and a "Branching Factor." It creates a perfectly structured, forward-flowing tech tree or questline from scratch.

Mode B: The Assessor (Analytical/Mutative)
You feed it an existing messy graph (like a dungeon generated by your Walker strategy). It analyzes it, prunes the cycles to make it a DAG, calculates the depth of every room, and mathematically distributes locks and keys so the dungeon is solvable.

1. The Lock & Key Distribution Engine (Constraint Solving)This is where the progression puzzle comes to life. We would build a function into the DAG Strategy that distributes items and locks across the graph using strict mathematical constraints:The Rule: If a door (Edge) or a boss (Node) requires "key_red" and is located at Depth $D$, the generator must place the item "key_red" in a room at Depth $K$, where $K < D$.The Implementation: We can write an algorithm that identifies choke points (Dominator Nodes) and dynamically places locks on those choke points, then scatters the required keys into the branches preceding them.

2. Logic Gates (AND / OR Nodes)Currently, our DAG assumes that reaching a node just requires following any single connected path. True tech trees and questlines require logic gates:AND Gates (Crafting/Rituals): A node that can only be traversed if all incoming edges are satisfied (e.g., you need the Hilt AND the Blade to craft the Sword).XOR Gates (Branching Narratives): A node that forces a mutually exclusive choice (e.g., you side with the Elves OR the Dwarves, closing the other path permanently).The Implementation: We would introduce semantic tags (like "logic_gate": "AND") and update the graph's metadata so that generators and agents understand how to evaluate these bottlenecks.

3. The Validator Agent (Automated Playtesting)Since we already have an Agent framework, we could build an AgentSolver. Instead of just wandering randomly, this agent reads the DAG from the Root node.It maintains an internal "Inventory" array.When it hits a locked edge, it checks its inventory. If it lacks the key, it backtracks to explore parallel branches.The Goal: A visual, automated unit test. You generate a massive DAG, press play, and watch an AI agent successfully solve the progression puzzle step-by-step, proving the math is sound.

### 3. Advanced Agent Graph Rewriting
**Goal:** Evolve agents from passive painters to active architects.
**Implementation:** Introduce cross-agent interactions and semantic-reading brains. Agents standing on the same node can trade data, merge nodes, sever edges, or spawn new branches based on the semantic properties of the zone they are currently occupying.






3. Sub-Graph Templating (The "Prefab" System)

For highly organized, reusable development, you need the ability to save and load structural fragments.

    The Concept: You lasso a "Boss Room" structure with your new Transform Box, and save it as a serialized template. You can then stamp that exact topological structure anywhere in the workspace.

    The Architecture: This requires designing a robust, localized schema for saving graph fragments (Nodes, Edges, relative positions, and metadata) and a clean injection protocol that automatically resolves ID collisions when a template is pasted into an existing graph.

GRAPH GRAMMAR UPGRADES:

1. Subgraph Isomorphism (N-Node Matching)The Limitation: Currently, your engine is locked to matching exactly two nodes (A and B). You cannot write a rule that says "Find a triangle of 3 nodes and put a hub in the middle," or "Find a sequence of 4 corridors."The Upgrade: We abstract _check_pair_match into a recursive subgraph matcher. The rule schema would define an array of required local edges (e.g., [["A", "B"], ["B", "C"], ["C", "A"]]). The engine would search for that exact topological signature, allowing you to mutate massive, complex prefabs all at once.

2. Stochastic & Iterative Growth (L-System Mechanics) The Limitation: The script currently finds every valid match in the graph and executes the rewrite simultaneously.The Upgrade: Add a probability (0.0 to 1.0) and an iteration_limit parameter to the rules. If a rule has a 10% chance to apply, or is capped at 3 executions per generation tick, you transition from deterministic modification into organic, unpredictable growth. This allows you to "grow" a dungeon frame-by-frame by running the grammar strategy in a loop.

3. Sequential Rule Pipelines (Grammar Recipes) The Limitation: You have to manually select one rule from the UI and execute it.The Upgrade: Introduce a "Pipeline" concept. A Pipeline is an array of rules executed in a specific order (e.g., 1. Expand Grid $\times5$, 2. Apply Boss Locks, 3. Cull Dead Ends). This allows you to script entire level generation routines purely through structural data design, without writing new GDScript for every map type.

4. Spatial Resolution Hooks The Limitation: When is_new spawns a node, it places it at the exact mathematical midpoint (pos_a + pos_b) / 2.0. In a dense graph, rewriting a few edges will cause multiple nodes to visually pile up on the same coordinate.The Upgrade: We can hook the grammar engine directly into your physics system. When the grammar injects a new node, it triggers a localized spatial relaxation (a quick burst of repulsive forces just for the new node and its immediate neighbors) so the graph automatically untangles itself during the rewrite process.
